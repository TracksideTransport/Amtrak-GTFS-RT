### zip — RUSTSEC\-2026\-0429

- Package: pkg:cargo/zip@6\.0\.0
- Installed version: 6\.0\.0
- Severity: high
- Dependency scope: runtime
- KEV status: not identified in CISA KEV
- Reachability: unreachable
- Decision reasons: proven\_unreachable
- Fixed versions: 9\.0\.0
- Advisory summary: \`ZipArchive::extract\(\)\` sizes the symlink\-target buffer from the uncompressed size declared in the central directory record, before reading a single byte of entry data:  \`\`\`rust let mut target = Vec::with\_capacity\(file\.size\(\) as usize\); \`\`\`  Both inputs are attacker\-controlled\. \`ZipFile::size\(\)\` returns \`uncompressed\_size\` verbatim from the central directory, widened to a full \`u64\` by a ZIP64 extended\-information extra field, and is never cross\-checked against the compressed size, the remaining archive length, or any platform\-appropriate bound for a symlink target\. \`ZipFile::is\_symlink\(\)\` is decided entirely by the \`S\_IFLNK\` bit of the external\-attributes field\.  \`Vec::with\_capacity\(\)\` is infallible: when the reservation is refused it calls \`handle\_alloc\_error\(\)\` and aborts the process\. This is not a Rust panic\. It is not caught by \`catch\_unwind\(\)\`, is unaffected by \`panic = &quot;unwind&quot;\`, and is not contained by running the call on a worker thread\.  A 112\-byte archive is sufficient\. One \`Stored\` entry flagged \`S\_IFLNK\` with a ZIP64 field declaring \`uncompressed\_size = 2^62\` and a zero\-byte payload makes \`extract\(\)\` fail with:  \`\`\` memory allocation of 4611686018427387904 bytes failed Aborted \(core dumped\)          \# exit 134 \`\`\`  The declared value only needs to exceed the host&\#x27;s address space, not its RAM: \`Vec::with\_capacity\(\)\` maps address space without touching pages, so resident memory stays flat and the abort happens on the refused reservation itself\. Under a \`ulimit \-v\` cap or a memory\-constrained container the threshold drops far enough that a plain 32\-bit \`uncompressed\_size\` with no ZIP64 field suffices\.  Applications that extract archives from untrusted input are affected on Unix and Windows targets with default features and no special configuration: upload handling, mail\-attachment processing, package and artefact ingestion, backup restore and container\-image layer extraction\. No confidentiality or integrity property is affected: there is no memory unsafety, no out\-of\-bounds access, no disclosure and no data corruption\.  The fix landed in \[zip\-rs/zip2\#984\]\(https://github\.com/zip\-rs/zip2/pull/984\) and shipped in 9\.0\.0\. ### zip — RUSTSEC\-2026\-0545

- Package: pkg:cargo/zip@6\.0\.0
- Installed version: 6\.0\.0
- Severity: critical
- Dependency scope: runtime
- KEV status: not identified in CISA KEV
- Reachability: unreachable
- Decision reasons: proven\_unreachable
- Fixed versions: 9\.0\.0, 9\.0\.5
- Advisory summary: For WinZip AES \(AE\-1 and AE\-2\) entries, the 10\-byte HMAC authentication code was read and checked only after the reader had consumed exactly the entry&\#x27;s declared compressed size\. If the archive ended before that size was reached, the read returned end\-of\-stream and the truncated plaintext was accepted without the check\. The authentication code of an entry with no encrypted data was never checked\.  AES\-CTR ciphertext can be changed bit by bit without the password, and AE\-2 entries carry no CRC\-32, so an attacker who can modify an archive can alter the decrypted contents of such an entry without any error being reported\.  This affects reading AES\-encrypted entries with a password \(for example \`ZipArchive::by\_name\_decrypt\`\) with the \`aes\-crypto\` feature\.  The fix returns an error when the data ends before the declared size, and checks the authentication code of empty entries\.
